# Run archives and result provenance

[Documentation](README.md) · [Getting started](GETTING_STARTED.md) · [Availability](../AVAILABILITY.md)

A complete run is the unit of experimental evidence. The same integrity contract
applies to the two bundled synthetic examples and to official-data runs,
including every run of a reproduction suite (`run_cross_morse.sh reproduce`,
[HPC guide](HPC.md)). Run archives are distributed as release assets
([release/paper_artifacts.json](../release/paper_artifacts.json),
[release/demo_artifacts.json](../release/demo_artifacts.json)); the tools below pack,
verify, ingest and rebuild tables from runs, including those a reproduction generates.
Keep every sealed file in a retained run; removing a checkpoint or inventory
breaks that run even when a summary table still exists.

## What a run must preserve

The eight stages are `prepare`, `train`, `explore`, `fit`, `select`, `confirm`,
`admit` and `evaluate`. Each stage records source/config/unit identities, input
and output hashes, and the previous stage's manifest under `provenance/stages/`.

| Evidence | Typical location |
|---|---|
| Prepared graph, labels, source hashes and exact role memberships | `prepared/` |
| Resolved configuration, seeds and environment | `config.json`, `environment.json` |
| Predictor histories, checkpoints and actual tensor inventory | `train/` |
| Exploration propensities and trajectories | `explore/` |
| Observer, critic, calibration and planning models | `fit/` |
| Complete candidates, predictions and selection decisions | `select/`, candidate/member prediction files |
| Confirmation, admission and locked policy | `confirm/`, `admit/`, `policy_lock.json` |
| Test predictions, paired units, metrics and intervals | `final/` |
| Stage-chain provenance and execution timings | `provenance/stages/`, `stages/` |

Independent comparison membership is allocated during preparation alongside the
other training roles. Exact IDs and hashes matter; split proportions alone do not
establish separation. Additional experiments have their own
[record contracts](../records/README.md).

## Three different verification operations

```bash
python -B scripts/artifact_inventory.py ../cm-runs/arxiv-full \
  --output ../cm-reports/arxiv-inventory.json
python -B scripts/reproduce_results.py ../cm-runs/arxiv-full \
  --output ../cm-reports/arxiv-replay.json
python -B scripts/evaluate_checkpoints.py ../cm-runs/arxiv-full \
  --trust-local-checkpoints --device cuda \
  --output ../cm-reports/arxiv-checkpoints.json
```

The inventory checks recorded artifacts and seals. Numerical replay recomputes
statistics and decisions from saved observations without loading models.
Checkpoint reexecution loads trusted checkpoints and verifies their predictions.
Use fresh report paths. The historical bundled runs retain their original source
snapshot so their replay does not pretend they were generated by the current code.

## Pack, deposit and ingest

```bash
make archive-run RUN_ROOT=../cm-runs/arxiv-full OUTPUT=../cm-deposits/arxiv-full.tar.gz
python -B scripts/archive_run.py --verify ../cm-deposits/arxiv-full.tar.gz
```

For Roman's complete ten-split campaign, use `make archive-campaign` with the
campaign directory. Packing verifies stage completeness and all sealed artifacts,
then writes `ARCHIVE_MANIFEST.json` and an archive checksum. Packing does not load
pickled model objects.

Preview the deposit before uploading. The client verifies the archive, streams
its bytes and derives metadata from the archive manifest and repository metadata.
Choose an archive license that applies to its contents; the software license does
not automatically cover prepared data from external providers.

```bash
make deposit-plan ARCHIVE=../cm-deposits/arxiv-full.tar.gz
read -r -p "Archive license ID: " ARCHIVE_LICENSE
read -r -s -p "Production Zenodo token: " ZENODO_TOKEN
export ZENODO_TOKEN
make deposit ARCHIVE=../cm-deposits/arxiv-full.tar.gz DEPOSIT_LICENSE="$ARCHIVE_LICENSE"
```

Inspect the draft's file and metadata before publication. The receipt next to the
archive preserves the deposit ID and binds it to the file hash, size, metadata
and service. Repeating the command reuses that deposit instead of creating a new
draft. Publication is a separate explicit step:

```bash
make deposit ARCHIVE=../cm-deposits/arxiv-full.tar.gz DEPOSIT_LICENSE="$ARCHIVE_LICENSE" PUBLISH=1
make ingest-run ARCHIVE=../cm-deposits/arxiv-full.tar.gz DOI=10.5281/zenodo.N
make runs-check
```

Replace the example DOI with the published **version DOI** from the verified
receipt. A reserved DOI belongs to a draft and does not establish public access.
The client keeps `reserved_doi` separate from `doi` and verifies the published
record before reporting publication as complete. `PUBLISH=0` does not publish.
If a request is interrupted, retain the receipt and rerun the same command.

Production receipts use `<archive>.deposit.json`. For a rehearsal, use
`SANDBOX=1` and a separate `ZENODO_SANDBOX_TOKEN`; sandbox receipts use
`<archive>.sandbox.deposit.json`. Sandbox identifiers are test identifiers and do
not enter the official evidence index. Zenodo describes the separate services,
tokens and publication states in its [API documentation](https://developers.zenodo.org/).

`make deposit-code` archives the clean committed `HEAD` as software; it uses the
repository's code license. After publishing, record the version DOI in
`release/release_scope.json` as `code_archive_doi`, then run
`make availability claims availability-statement`. The deposit identifies the
archived commit; a later metadata commit does not change those archived bytes.

`make fetch-deposits` is the reviewer-side check. It examines registered public
records, matches the exact version DOI, filename and byte count, downloads as
needed, and verifies SHA-256 and archive contents. The authoritative index and
availability documents are preserved. Runs are materialized alongside the
selected index; conflicting local runs are preserved unless an explicit repair
is requested. `make review` writes fresh reports and rebuilt displays in its own
output workspace and records those paths.

Ingestion verifies and extracts the archive, then registers its identity and DOI
in `runs/index.json`. Generated run payloads are Git-ignored; the index identifies
the externally deposited observations. `make ingest-run` also refreshes per-run
manifests and the generated availability page, claims ledger, badge and manuscript
paragraph. Source code and large experiment deposits need not
share the same hosting location.

For several completed runs, the [evidence-registration workflow](EVIDENCE_REGISTRATION.md)
applies scientific preflight before packing and manages these steps from one
private plan. A fresh clone can verify a registered archive's committed manifest
and index without downloading its payload. This is a metadata check: public access
and deposited bytes are checked by `make fetch-deposits` and `make review`.
Any payload already present is verified in full.

## Build and compare results

```bash
make paper
make compare-runs
make scientific-audit BUDGET_CAMPAIGN=/path/to/e3-e6-campaign
```

`make paper` builds run-derived tables/figures and record-derived tables from the
applicable ingested evidence. The manuscript registry is a comparison target,
not a substitute data source. A quantity not measured by the runner remains
missing rather than being filled with a transcribed paper value.

`make compare-runs` compares run-derived outcomes with reported values and checks
sealed checkpoint inventories against S5, including all ten Roman splits. The
scientific audit additionally checks role evidence, complete measurement coverage
and declared manuscript bindings. `scripts/compare_with_manuscript.py
--emit-binding` prepares a binding record, checked by
`scripts/check_result_binding.py`; declaring a relationship still requires the
actual observations and source identity.

`make review REQUIRE_EVIDENCE=1` additionally requires its full set of evidence
checks. Supply the campaign and matching PDF paths as shown in the
[reviewer guide](REVIEWER_GUIDE.md). Seven registered archives alone do not supply
the ten auxiliary record sets or complete every manuscript binding.

These are separate claims:

1. Files match their declared hashes and the stage chain is intact.
2. The run identifies the exact computation source that produced it.
3. The observations are the ones underlying a particular reported result.

A checksum establishes byte identity. A numerical match alone does not establish
experimental origin. The binding and deposited records make that origin inspectable.

## Records outside the core lifecycle

E3–E6 comparisons, external baseline reruns, timing, input gates, factorials,
negative controls, ensemble grids, cross-backbone and attribution studies supply
raw observations and traced summaries under the [records contract](../records/README.md).
`make records-check` re-reads summary values from their raw files. See
[Experiments](EXPERIMENTS.md) for execution and export.

After exporting records, `make records-index` updates their index and generated
availability views. `make records-tables` writes outputs by **record-set name**,
for example `paper/generated/official/records/baselines.tex` and
`budget_matched.tex`; their captions identify the manuscript tables they support.

When the final manuscript changes, review affected numerical targets and page
mappings, then use the [PDF registration steps](EVIDENCE_REGISTRATION.md#7-review-and-register-the-final-pdfs).
`scripts/check_manuscript_sources.py` remains the read-only check of PDF bytes
against registered identities. PDFs remain outside the repository.

After authoring or registering new evidence, refresh the generated views before
the source checksums, then verify the release:

```bash
make availability claims availability-statement manifest
make verify
```
